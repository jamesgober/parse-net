# parse-net v0.10.0 - A simpler API

**Date:** 2026-11-11
**Compare:** [`v0.9.3...v0.10.0`](https://github.com/jamesgober/parse-net/compare/v0.9.3...v0.10.0)

**A simpler API before 1.0, security fixes, and negotiation that follows the RFCs.** I went through all 575 public items of `0.9.3` with four rules in mind: a Tier 1 call covers most uses in one line with plain `?` and no configuration; a name reads without the docs; there is one way to do each thing; and the API reference names every public item. Thirteen places broke a rule. `0.10.0` fixes all thirteen.

**This release breaks code on purpose.** There are no deprecated aliases, because they would carry two ways to do each thing into 1.0. The compiler names each call that needs changing, and [`docs/MIGRATION.md`](../MIGRATION.md) gives its replacement.

**Security.** The most serious fix is in `client_address`: a client could make its requests look like they came from the trusted proxy. There are also fixes to file names in `Content-Disposition`, `Cache-Control`, and `Host` (below). Each one has a regression test.

**Content negotiation follows the RFCs.** Issue #14 reported four `Accept` and `Accept-Language` cases. I checked each against RFC 9110 and RFC 4647. All four were real bugs, and all four are fixed (below).

## Changed

- **Root parsers are all `parse_*`.** A newcomer who had met `parse_media_type` would guess `parse_list` and find nothing.

  | 0.9 | 0.10 |
  |---|---|
  | `list(value)` | `parse_list(value)` |
  | `http_date(value)`, `http_date_at(value, now)` | `parse_http_date(value)`, `parse_http_date_at(value, now)` |
  | `response_cache_control(value)`, `request_cache_control(value)` | `parse_response_cache_control(value)`, `parse_request_cache_control(value)` |

  Functions named for their answer keep their names: `best_media`, `if_none_match`, `byte_ranges`, `client_address`, `bearer`.
- **Tier 1 calls take no `Limits`.** Each one uses `Limits::DEFAULT`. The full form keeps the argument: it is either the module's `parse(value, &limits)` or the call's `_with_limits` form.
  - `parse_link(value)`; the full form is `link::parse(value, &limits)`.
  - `mail::parse_mailbox(value)`, `mail::decode_words(value, out)`, `mail::decode_phrase(value, out)`; the full forms are `parse_mailbox_with_limits`, `decode_words_with_limits`, and `decode_phrase_with_limits`.
  - `parse_condition` is no longer at the crate root. It needed a `Limits`, and `if_match` and `if_none_match` give the answer in one call. The full form is `etag::parse(value, &limits)`.
- **One way to do each thing.**
  - `HttpDate::parse_at` is gone: it was `parse_http_date_at` under a second name. `HttpDate::parse_at_with` is now `HttpDate::parse_with_limits`.
- **No boolean arguments to decode at the call site.**
  - `MailDate::parse(value, false)` is now `MailDate::parse(value)`.
  - `MailDate::parse(value, true)` is now `MailDate::parse_obsolete(value)`.
- **Words, not abbreviations.**

  | 0.9 | 0.10 |
  |---|---|
  | `pct` | `percent` |
  | `pct::decode_lower_only_into` | `percent::decode_lowercase_into` |
  | `sfv` | `structured` |
  | `ext_value`, `ExtValue`, `write_ext_value` | `extended_value`, `ExtendedValue`, `write_extended_value` |
  | `mail::encode_words_b` | `mail::encode_words_base64` |
  | `forwarded::XffChain` | `forwarded::XForwardedFor` |

- **`client_address` cannot fail, and takes no hop count.** It returns `ClientAddress`; `forwarded::client_address_with_limits` takes `&Limits` (`max_hops`), as does `client_address_detailed`.
- **`if_match` and `if_none_match` take a `Representation`**: `Absent`, `Untagged`, or `Tagged(tag)`. `PUT` with `If-None-Match: *` needs "nothing is there", and a representation without a tag had no form at all (RFC 9110 section 13.1.2).
- **`HostPort`, `Origin`, `forwarded::Element`, `Host`, and `forwarded::Node` are `#[non_exhaustive]`**, so 1.x can add a field or variant. `HostPort::new`, `Origin::new`, and `Element::new` build them.
- **Owned forms come from `into_owned`**, not `to_owned`: the views are `Copy`, so `ToOwned::to_owned` applied to them too and returned a view.
- **`ErrorKind::ForbiddenParameter`** is new (below).
- **Several-line forms are `parse_*_lines`.** `list::combined` is now `list::parse_lines`. `cache::response_lines` and `cache::request_lines` are now `cache::parse_response_lines` and `cache::parse_request_lines`. This matches `structured::parse_list_lines`.

```rust
use parse_net as pn;

let codings = pn::parse_list(b"gzip, br")?;
let links = pn::parse_link(b"<https://example.com/2>; rel=next")?;
let m = pn::mail::parse_mailbox(b"Jane Doe <jane@example.com>")?;
let mut subject = [0u8; 64];
assert_eq!(pn::mail::decode_words(b"=?UTF-8?Q?Caf=C3=A9?=", &mut subject)?, "Caf\u{e9}");
# let _ = (codings, links, m);
# Ok::<(), parse_net::ParseError>(())
```

## Security

| Problem | `0.9.3` | `0.10.0` |
|---|---|---|
| `client_address` | read and counted the whole chain, though everything left of the first untrusted address is the client's own text. `x, 198.51.100.7`, an upstream `unknown`, or 16 padding entries made it fail, and the docs said to use the peer then: the trusted proxy, often exempt from rate limits and bans | walks from the right and reads nothing past the client. An entry there with no reliable address, or more trusted hops than the limit, is `ClientAddress::Unknown`, which the docs say never to replace with the peer |
| `filename*` in `form-data` | preferred over `filename`, so `filename="shell.php"; filename*=UTF-8''avatar.png` passed a check as `avatar.png` while a backend reading `filename` stored `shell.php` | refused with `ForbiddenParameter`: RFC 7578 forbids it and browsers never send it |
| RFC 2231 continuations | `filename*0`, `filename*1` ignored by `parse_content_disposition` and joined by `mail::parse_mime_params`: two names for one header | refused in `Content-Disposition`; `name*` beside `name*0` refused in MIME parameters |
| quoted-pair separators | `filename="..\..\web.config"` decodes to `....web.config`, and `has_path_separator` said no; browsers mean the backslashes | flagged: a quoted name is also checked before unescaping |
| one bad `Cache-Control` directive | `private, no-store, ext=a b` refused the field, and a cache treating it as absent lost `no-store` | the struct readers skip the directive and set `invalid_values` |
| escaped hosts | `a%00b.example` and `%61dmin.example` accepted and compared raw, while browsers decode first | any `%` in a reg-name is `InvalidHost` |

## Fixed

- `Link`: a quoted pair in `rel` (`rel="pre\load"`) is refused; `rel` and `has_rel` read it two ways.
- `MimeParams::decode_into` refuses HTAB and C1 in a plain value, as every decoder does.
- `mail::parse_addr_spec` refuses C1 controls.
- `mail::parse_mailbox` reads a fold between the words of a display name.
- `encode_words` and `encode_words_base64` never start with a fold: with no room for one character, the first word holds it and runs past the room. A leading fold read back as a leading space.

All four cases from issue #14 are fixed at the root, each checked against the RFC text, each with a regression test. Property tests now compare both selections with plain reference readers of the RFCs: one sorts the ranges and truncates them, the other takes the most specific matching range.

| Header | Offers | `0.9.3` | `0.10.0` | Rule |
|---|---|---|---|---|
| `text/html;a=1;q=1, text/html;a=1;b=2;q=0` | `text/html;a=1;b=2` | chosen, weight 1 | not acceptable | RFC 9110 section 12.5.1: the most specific range has precedence |
| `text/html;q=1;level=2` | `text/html;level=1`, `text/html;level=2` | the first | the second | RFC 9110 section 12.5.1: read `q` as the weight regardless of parameter order |
| `en-US;q=1, en;q=0.1, fr;q=0.5` | `en`, `fr` | `fr`, weight 0.5 | `en`, weight 1 | RFC 4647 section 3.4: a range is truncated before the next range is tried |
| `*;q=1, fr;q=0.5` | `en`, `fr` | `en` | `fr` | RFC 4647 section 3.4: a `*` followed by other ranges is skipped |

- `MediaRange::specificity` now orders ranges by parameter count within each level (an exact type over `type/*` over `*/*`). Only its order is meaningful; its numbers changed.
- `MediaRange::params` returns `media::RangeParams`: every parameter but `q`, before or after it. It has the same `iter`, `get`, `len`, and `is_empty` as before.
- Lookup also refuses any offer equal to a `q=0` range, however a higher range would reach it. With `en-US, en;q=0` and the offer `en`, nothing is acceptable.
- Basic filtering, `Accept-Encoding`, and `Accept-Charset` are unchanged. Basic filtering keeps the `*` rule of RFC 2616 (`*` matches every tag no other range matched); RFC 9110 section 12.5.4 hands matching to RFC 4647, whose lookup skips a `*` that other ranges follow.

## Documentation

- **The crate documentation and the README** show the whole Tier 1 as compiled examples, email included. Both used to end with an uncompiled block saying those calls "arrive with 0.4.0 and 0.5.0", though they shipped long ago.
- **`docs/API.md`** has the title block and navigation of the other first-party API references, names the current release, and states the naming rule. It now names every one of the 635 public items, and a check before each release keeps it that way. All 36 of its examples compile and pass against the release.
- **`docs/MIGRATION.md`** opens with the 0.9 to 0.10 tables: by call, by signature, by behaviour, and by consumer.
- **What the caller decides** is now written down where it was only implied: how mail readers differ on RFC 2047, the bidirectional marks and Windows names `has_bidi_control` leaves alone, what an email address means beyond its grammar, weak dates in `IfRange::matches`, `Dictionary::iter` against `get`, and `percent::encode` with a set that lacks `%`.

## Performance

Instructions per call (callgrind), `0.9.3` against `0.10.0`, built side by side from the same driver:

- **The renames:** every row is within one instruction of `0.9.3`. The new one-line Tier 1 calls are inlined into the full forms.
- **Negotiation:** issue #14's fixes rewrote it, and every row is faster than `0.9.3`.
  - `best_media` on a browser `Accept`: 10,861 to 10,702 (-1.5%).
  - `best_media` on four ranges with parameters: 8,014 to 7,959 (-0.7%).
  - `best_language` on five ranges: 10,547 to 9,990 (-5.3%).

The first version of the lookup fix cost 26%, from an extra walk over the ranges; it was rewritten to need none.

- **The security fixes:**

  | Call | `0.9.3` | `0.10.0` | |
  |---|---|---|---|
  | `client_address`, 3-hop `X-Forwarded-For` | 1,314 | 913 | -30.5% |
  | `client_address`, 2-element `Forwarded` | 5,350 | 3,077 | -42.5% |
  | `parse_response_cache_control` | 835 | 801 | -4.1% |
  | `mail::parse_mailbox` | 1,622 | 1,562 | -3.7% |
  | `parse_host_port` | 469 | 453 | -3.4% |
  | `parse_content_disposition` with `filename*` | 3,597 | 3,703 | +2.9% |
  | `parse_content_disposition`, `form-data` | 2,370 | 2,445 | +3.2% |
  | `if_none_match`, 3 tags | 527 | 530 | +0.6% |
  | `mail::encode_words` | 5,716 | 5,755 | +0.7% |

  `client_address` is faster because it reads less: it stops at the client. The `Content-Disposition` cost is the search for RFC 2231 continuations, two byte searches over the parameters (a full walk over the parameters cost 7%). The first versions of the `Cache-Control` and `parse_mailbox` changes cost 4% to 10%; a visitor in place of an `Option` callback, a fast path in the display-name trim, and a C1 check folded into the existing byte loop made both faster than `0.9.3`.

## Testing

- Every unit, property, integration, and documentation test passed with the new names. Tests changed only for the names, the new signatures, and the behaviour this release changes on purpose: eight tc2231 continuation cases now expect `ForbiddenParameter`, and one host vector expects `InvalidHost`.
- A regression test for each fix, and a property test comparing the new `client_address` walk with a collect-then-walk reference, quoted commas and unclosed quotes included. The `xff` and `forwarded` fuzz targets now assert that no text left of the address a trusted proxy appended changes the answer.
- Doc tests cover each new Tier 1 call, and the `MailDate::parse_obsolete` example checks it against `MailDate::parse`.

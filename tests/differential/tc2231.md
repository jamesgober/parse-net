# tc2231 verdicts

Every case of the greenbytes test suite for `Content-Disposition` and RFC 5987
encoding ([tc2231](https://greenbytes.de/tech/tc2231/)), with the behaviour
the suite expects of a browser, what `parse_content_disposition` returns, and
the verdict. The same cases, with the exact header bytes, run in
`tests/vectors.rs` from `tests/vectors/content_disposition.txt`.

parse-net reports facts and leaves policy to the caller (dev/PLAN.md section
10.2): it returns the disposition type and the decoded file name, and
`Filename::has_path_separator` and `has_bidi_control` for the checks a caller
must make before using the name. A browser's choices (treat an unknown type as
`attachment`, drop a path, fall back to "no name") are the caller's.

## Deviation classes

| Class | Cases | parse-net | Why |
|---|---|---|---|
| C-1 | 2 | an empty parameter (`;;`, trailing `;`) is accepted | RFC 9110 section 5.6.6 defines `parameters = *( OWS ";" OWS [ parameter ] )`, which allows empty parameters, and parse-net applies that rule to every parameterized field. RFC 6266's grammar (from RFC 2616) does not allow them. The value read is the same either way; nothing is hidden by the extra `;`. **Ambiguous**, kept |
| C-2 | 3 | whitespace around `=` refuses the field | RFC 9110 section 5.6.6: "Parameters do not allow whitespace (not even "bad" whitespace) around the "=" character." The suite follows RFC 2616's implied linear whitespace. **Ours right** under RFC 9110; one of the whitespace differentials of threat T6 |
| C-3 | 7 | RFC 2231 continuations (`filename*0=`) are not joined: no file name | RFC 6266 section 4.3 adopts RFC 5987 (now RFC 8187) only, which excludes the continuations of RFC 2231 section 3. Continuations are a mail feature (the 0.5 MIME parameter layer). **Ours right** for HTTP |
| C-4 | 2 | a plain `filename` with bytes that are not UTF-8 parses, and `decode_into` refuses it with `InvalidUtf8` | parse-net does not guess a charset for `obs-text`: browsers disagree on it (compare `attwithutf8fnplain`), and a guessed name is a spoofing risk. The raw bytes stay available through `Filename::Plain`. **Deliberate** (D-010 covers the `filename*` side) |
| C-5 | 7 | an invalid `filename*` refuses the whole field | browsers drop the one parameter and keep the rest. parse-net validates a field as a whole (`filename*` is decoded during the parse, so a view never holds an undecodable name); a caller that wants the browser behaviour treats the refusal as `attachment` without a name. **Deliberate**: same outcome for the user, no half-trusted view |

Every other case agrees with the expected behaviour.
